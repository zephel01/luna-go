---
name: code-review
description: 指定したファイルまたは git diff の変更をレビューし、問題点・改善案・良い点をまとめる
---

## 手順

### 引数がある場合（ファイル名や PR 番号が指定された場合）

1. 指定されたファイルを `read` で読む。
2. 変更の意図が不明な場合は `bash({"command": "git log --oneline -5 <file>"})` でコミット履歴を確認する。

### 引数がない場合（カレントブランチの変更をレビュー）

1. `bash({"command": "git diff main...HEAD --stat"})` で変更ファイルの一覧を確認する。
2. `bash({"command": "git diff main...HEAD"})` で差分全体を取得する。
3. ファイル数が多い場合は重要度の高いファイルから順に `read` で読む。

### レビューの観点

以下の観点で分析し、**Markdown 形式**でレポートを出力する。

#### 🔴 問題（修正必須）
- バグ・ロジックエラー
- セキュリティリスク（SQL injection, path traversal, 認証バイパス等）
- データ競合・デッドロックの可能性
- nil ポインタ参照の可能性

#### 🟡 提案（改善推奨）
- エラーハンドリングの欠落・不適切な処理
- 重複コード・DRY 原則違反
- パフォーマンス上の懸念（不要なアロケーション等）
- テストが不足している箇所

#### 🟢 良い点
- 適切な抽象化・シンプルな実装
- 明確な命名
- 丁寧なエラーメッセージ

#### ℹ️ 情報
- 設計上のトレードオフや考慮点
- 将来的な拡張への影響

## 出力形式

```markdown
## コードレビュー: <対象>

### 変更概要
<何をしているかの要約>

### 🔴 問題
- **[ファイル:行]** <問題の説明>
  ```go
  // 問題のあるコード
  ```
  → 修正案: ...

### 🟡 提案
...

### 🟢 良い点
...

### 総評
<全体的な評価と優先対応事項>
```

## 注意

- 問題がない場合は「問題なし」と明記する（省略は不可）。
- 修正案を示す場合は、具体的なコードスニペットを添える。
- スタイルの好みを押し付けない。明確なバグや設計問題に集中する。
